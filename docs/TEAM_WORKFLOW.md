# Работа вдвоём: GitHub и VS Code

Репозиторий команды: https://github.com/BAITC-Hacks/hack-acbb98e4-she

Каждый участник работает на своём компьютере и под своим GitHub-аккаунтом.
Каждый самостоятельно пишет, проверяет и объясняет свою часть решения, затем делает коммит.
История Git подтверждает изменения и авторов, но сама по себе не доказывает работу с двух устройств.
Не создавайте коммиты от имени другого человека и не переносите ему готовые изменения ради видимости вклада.

Статус реализации и актуальные команды запуска смотрите в [README](../README.md).
Стартовый пакет организаторов добавлен в репозиторий; наличие файлов не подтверждает итоговую оценку.
Пользуйтесь фактическими результатами проверок и актуальными условиями сдачи из пакета.
Эта инструкция описывает совместную работу; она не обещает оценку или готовность решения.

## 1. Открыть проект на каждом компьютере

1. Убедитесь, что оба GitHub-аккаунта имеют доступ к репозиторию и приглашения приняты.
2. Откройте **Visual Studio Code**. Если папка проекта уже открыта, повторно клонировать не нужно.
3. Иначе нажмите `Cmd+Shift+P` на macOS или `Ctrl+Shift+P` на Windows.
4. Найдите **Git: Clone**, вставьте `https://github.com/BAITC-Hacks/hack-acbb98e4-she.git`.
5. Выберите папку для проекта, подтвердите вход своим аккаунтом и нажмите **Open / Открыть**.
6. Для уже скачанной папки используйте **File → Open Folder / Файл → Открыть папку**.
7. Откройте **Terminal → New Terminal / Терминал → Создать терминал**.

Проверьте, что терминал находится в папке репозитория:

```bash
git status
git branch --show-current
git config --get user.name
git config --get user.email
```

Если имя или почта отсутствуют либо принадлежат другому человеку, задайте **свои реальные данные только для этого репозитория**:

```bash
git config --local user.name "Ваше имя"
git config --local user.email "Ваша подтверждённая GitHub-почта"
```

Замените текст в кавычках своими значениями. Можно использовать личный адрес `noreply` из GitHub → Settings → Emails.
Не используйте `--global`, чужое имя или чужую почту. Автор коммита и аккаунт для отправки в GitHub — разные настройки.

## 2. Разделить работу до редактирования

| Участник | Личная задача | Как показать вклад |
| --- | --- | --- |
| 1 | Разобрать агента и журнал его решений, выбрать и реализовать обоснованное улучшение стратегии после наблюдения пилотов. | Объяснить изменение, сравнить поведение до/после и проверить ограничения. |
| 2 | Расширить независимые стресс-тесты: частичный сбой пилотного API, изменение стоимости каналов, противоречивые повторные пилоты. | Самостоятельно написать проверяемые сценарии, найти и исправить ошибки, если они обнаружатся. |

До начала согласуйте интерфейс: формат плана, типы значений и описание ошибок.
Общий стартовый код подготовлен с помощью Codex. Уже созданные файлы не доказывают личный вклад второго участника.
Участник 1 отвечает за улучшения агента; участник 2 — за расширение проверок и тестов на своём устройстве.
Проверяющий модуль не должен просто вызывать ту же функцию проверки, которую тестирует: это не выявит общую ошибку.
Ожидаемые результаты тестов выводите из ТЗ и небольших примеров, которые можно проверить вручную.
Записывайте реальные команды и результаты. Локальная проверка не является оценкой организаторов.
Изменение общего интерфейса, README или настроек заранее согласуйте; один файл одновременно редактирует один человек.

## 3. Создать свою ветку

Начинайте после того, как общий каркас окажется в `main`. В терминале каждого компьютера:

```bash
git status
git switch main
git pull --ff-only origin main
```

Если `git status` показывает незакоммиченные изменения, сначала сохраните их коммитом в своей текущей ветке.
Не удаляйте изменения и не переключайте ветку принудительно.

Участник 1 выполняет:

```bash
git switch -c participant-1/agent
```

Участник 2 выполняет:

```bash
git switch -c participant-2/validation
```

Если ветка уже создана, используйте `git switch имя-ветки` без `-c`.
В VS Code текущая ветка отображается слева внизу; проверьте её перед редактированием.

## 4. Сохранить и отправить собственные изменения

1. Измените свою часть кода и выполните относящиеся к ней проверки по актуальному README.
2. Откройте **Source Control / Управление версиями** слева (`Ctrl+Shift+G`; на macOS также доступно через меню View).
3. Нажмите на каждый изменённый файл и проверьте разницу. Не включайте токены, пароли, `.env` или данные с ограничением распространения.
4. Нажмите **+** рядом только с файлами своей задачи, чтобы подготовить их к коммиту.
5. Введите конкретное сообщение, например `Добавлена проверка превышения бюджета`, и нажмите **Commit**.
6. Нажмите **Publish Branch / Опубликовать ветку** при первой отправке; далее **… → Push / Отправить**.
7. Откройте репозиторий на GitHub, нажмите **Compare & pull request** для своей ветки.
8. Проверьте: базовая ветка — `main`, исходная — ваша. Укажите изменения, реальные проверки и известные ограничения.
9. Нажмите **Create pull request** и попросите напарника просмотреть код и воспроизвести проверку на своём компьютере.

Коммит сохраняет работу локально; **Push** отправляет её на GitHub; **Pull request** предлагает добавить её в `main`.
После проверки объедините PR через **Create a merge commit**, если этот способ разрешён в репозитории, чтобы сохранить отдельные коммиты участников.

## 5. Забрать изменения напарника и избежать конфликтов

После объединения PR и при чистом `git status` обновите локальную `main`:

```bash
git switch main
git pull --ff-only origin main
git switch participant-2/validation
git merge main
```

Последние две команды — пример для участника 2; участник 1 подставляет `participant-1/agent`.
При конфликте VS Code покажет **Merge Changes**. Вместе разберите смысл обеих версий, сохраните нужное поведение, повторите проверки и сделайте коммит.
Не выбирайте автоматически «Accept All», не используйте `push --force` и не удаляйте чужую работу.
Перед сдачей оба участника обновляют `main`, повторяют сценарий из README и умеют объяснить собственные изменения.
